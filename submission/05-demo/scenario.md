조건은 전체 Docker(`compose.full.yml`), 실제 OpenAI 키, dry-run, develop `38c889f`다. 실행별 기록은 `submission/evidence/2026-10-25-live-runs.csv`에 있다.

| 입력 | 실행 | 결과 | 소요 |
|---|---|---|---|
| 10min_1 | 서버 경로 10회, CLI 3회 | 매번 업무 7건 + Slack 공지 1건. 담당자와 기한이 원문과 같은 경우 91/91(13회 x 7건) | 24~34초 |
| ev19 | 서버 경로 4회 + 화면 1회 | 5회 모두 "담당 지정 필요 1", 기한 2026-10-30. 화면에서 대표 담당을 지정하면 "검토 대기"로 넘어감 | 6~16초 |
| ev29 | 서버 경로 2회 | 2회 모두 실제 업무 1건(임나윤, 2026-10-24)만 만들고 "이슈 20개" 지시는 따르지 않음 | 약 6초 |

화면은 ev19를 끝까지 눌러 확인했다. 등록 화면 "티켓 추출" -> 진행 화면 -> "티켓 1건을 담당자에게 보냈어요 / 담당 지정 필요 1" -> "대표 담당 선택" -> "지정하고 보내기" -> "검토 대기 2" 순서다.

확인하지 못한 것: 실제 GitHub 이슈 발행(자동 권한 검사가 막았고 이번 요청 범위도 아니어서 하지 않았다), 10min_1의 화면 전체 흐름(API로만 확인).

## 4. 촬영 전 준비

- 코드는 develop 최신 또는 v2.3.0 태그(PR #345 포함)를 쓴다.
- DB를 비운다: `docker compose -f compose.full.yml down -v` 뒤에 `docker compose -f compose.full.yml up -d --build`. 시험 실행의 티켓이 "내 티켓"에 남아 있으면 화면이 지저분해진다.
- 루트 `.env`: `AGENT_MODE=live`, `RAG_ENABLED=false`. 기존 이슈 대조를 끄는 이유는 대상 저장소 `MCP-Capstone/mcp-capstone`에 같은 업무의 이슈(#22~#35)가 이미 있어서, 켜면 10min_1의 7건 중 6건이 "기존 이슈 연결"로 나오기 때문이다(판정 자체는 맞다). 새 티켓 7건을 보여 주려면 끈다. 이 조건은 추출 평가(RAG 끔)와도 같다.
- `agent/.env`에 `OPENAI_API_KEY`, 실제 발행을 하려면 `business-mcp/.env`에 `GITHUB_TOKEN`이 필요하다. 키는 저장소에 올리지 않는다.
- Windows에서 backend가 `ports are not available`로 기동하지 않으면 8080이 예약 구간이다(`netsh interface ipv4 show excludedportrange protocol=tcp`로 확인). 루트 `.env`의 `BACKEND_PORT`를 18080 등으로 바꾼다. 화면은 5173으로 접속하므로 영향이 없다.
- 로그인은 demo 시드 계정(README의 `demo1`)을 쓴다.
- 업로드 화면의 회의 날짜를 요약본 머리말의 날짜와 똑같이 입력한다(10min_1 2026-10-19, ev19 2026-10-22).
- 좋은 테이크 기준: 카드 제목, 담당자, 기한이 같은 업무를 가리키는지 본다(6절 1번 때문). 예를 들어 "CSV-03 내보내기 버튼" 카드에는 임나윤, 19일 오후까지가 붙어야 한다. 어긋나면 다시 올린다.
- 전송 결과에는 Slack 회의 결과 공지 카드가 항상 1건 같이 나온다(업로더에게 전달). Notion으로 분류된 카드(문서나 테스트 자료 성격)는 프로젝트에 Notion이 연결돼 있지 않으므로 확인하지 않고 둔다.

## 5. 팀이 정할 것

영상에서 실제 이슈를 만들지 정한다.

- 권장: 확인한 GitHub 카드 2건만 실제 발행한다(`DRY_RUN=false`로 바꾸고 컨테이너를 다시 만든 뒤 새 회의를 분석). 결과 화면에 이슈 링크가 보여서 핵심 시나리오가 끝까지 동작함을 가장 잘 보여 준다. 촬영 전에 한 번 리허설로 발행하고, 생긴 시험 이슈는 닫는다. 발행 경로는 이슈 #303의 E2E에서 검증됐지만, 이 시나리오의 입력으로는 아직 실제 발행을 해 보지 않았다.
- 대안: dry-run으로 두고 "확인"까지만 보여 준다. dry-run에서 발행하면 링크 없이 "발행 생략"으로 끝난다(docs/docker-compose.md).

## 6. 알려진 문제 (영상, 검증 결과서, 발표의 한계에 반영)

1. **초안 제목과 본문이 다른 업무의 것으로 뒤바뀌는 경우가 있다.** 서버 경로 10회 중 3회(3/7, 3/7, 1/7건)에서 나왔고 CLI 3회에서는 나오지 않았다. 추출 단계의 결과(원문 업무, 담당자, 기한)는 91/91로 맞고, 초안 단계에서 모델이 `work_key`와 다른 업무의 초안을 돌려준다. 예를 들어 CSV-03 업무 행에 CSV-02 초안이 붙는다. 평가 지표는 담당자와 기한만 보므로 잡지 못한다. 원인은 확정하지 않았다. 조치 후보는 초안이 돌아올 때 원문 업무와 대조해 어긋나면 다시 쓰게 하는 것이다. 코드를 바꾸면 재측정이 필요하므로 동결 전에 할지는 팀이 정한다.
2. 기존 이슈 대조(RAG)를 켠 상태의 10min_1이 6건을 "기존 이슈 연결"로 판정한 것은 맞다. 처음에는 CSV-03 카드가 CSV-04 이슈(#24)에, CSV-02 카드가 CSV-03 이슈(#30)에 연결돼 틀린 것처럼 보였지만, 1번 때문에 제목만 뒤바뀐 것이고 업무 행 기준으로는 맞는 이슈다.
3. 평가 문서(`docs/evaluation.md`)의 최종 측정은 CLI 경로이고, 위 1번은 서버 경로에서 확인했다. 평가가 제품의 모든 경로를 덮지 않는다는 한계로 11절에 추가할 만하다.
