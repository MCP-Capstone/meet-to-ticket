# 발표자료 (7장)

문제 - 해결 - 결과 - 한계 순서이고 7장이 팀 역할과 기여다. 아래 7개 슬라이드 뒤에 15분 대본과 예상 질문이 있다. 슬라이드는 `submission/tools/build_pdf.py`로 PDF(가로 페이지)로 만든다.

## 슬라이드 1. 문제: 회의가 끝나도 티켓은 누가 만들지 모른다

- 회의에서 업무가 정해져도 누가 티켓으로 옮길지는 정해져 있지 않다
- 그 결과 결정사항이 빠지고, 기존 이슈와 중복된 티켓이 생기고, 근거가 티켓에 남지 않는다
- 사용자: 후속 업무를 맡는 담당자(개발자, 디자이너, 기획자)와 회의록을 올리는 업로더
- 현황을 잰 수치는 없다. 팀 프로젝트 경험에서 나온 가정이다

## 슬라이드 2. 해결: 회의록에서 담당자 확인까지 한 흐름으로

- 회의록 업로드 -> AI가 할 일 추출과 초안 작성 -> 기존 이슈와 대조 -> 담당자별 전송 -> 담당자 확인 -> 확인한 건만 일괄 발행
- AI가 맡는 일: 할 일(업무, 담당자, 기한, 회의록 원문 근거)을 뽑고, 같은 업무의 기존 이슈가 있는지 판단한다
- 사람이 정하는 일: 확인, 수정, 거절, 발행. 모르면 멈춘다(담당자 미정이면 "담당 지정 필요")
- 발행 대상: GitHub 이슈, Notion 페이지, Slack 회의 결과 공지

## 슬라이드 3. 구성: 실제 코드 구조 그대로

![시스템 구성도](../01-design/architecture.svg)

- LLM(OpenAI): 서술형 회의록에서 업무 추출, 초안, 검수, 중복 판단
- LangGraph: 추출 -> 초안 -> 검수(최대 2회 보완) -> 중복 판단 -> 저장
- MCP: GitHub, Notion, Slack 발행과 조회를 도구로 분리, 쓰기 저장소는 설정으로 제한
- RAG(Chroma): 기존 이슈의 의미 검색으로 같은 업무를 찾는다

## 슬라이드 4. 검증 방법: 같은 평가셋으로 개선 전과 후

- 평가셋 v2.1: 입력 30개, 채점 단위 37문항(할 일 0건, 철회, 인젝션, 개인정보, 담당 미정 같은 실패 유도 포함)
- 문항마다 3회 실행, 개선 전은 `phase1-end` 태그, 개선 후는 develop `29a3a22`
- 지표: 추출 정밀도, 기한 정확도, 중복 판단 정확도(판정과 대상), 업무 재현율, 처리 시간
- 항상 dry-run, 같은 모델과 같은 조건(추출은 RAG 끔, 중복 판단은 RAG 켬)

## 슬라이드 5. 결과: 기한은 크게, 추출과 중복 판단은 목표 안으로

| 지표 | 개선 전 | 개선 후 | 목표 |
|---|---|---|---|
| 기한 정확도 | 17.8% | 96.1% | 90% 이상 |
| 추출 정밀도 | 71.1% | 80.3% | 80% 이상 |
| 중복 판단 정확도 | 83.3% (15/18) | 100% (18/18), 94.4% (17/18) | 90% 이상 |
| 담당자 오류율 | 3.0% | 0.0% | 5% 이하 |
| 문항 충족(추출, 회차) | 20.8% (15/72) | 72.2% (52/72) | 목표 없음 |
| 업무 재현율 | 96.2% | 97.1% | 90% 이상 유지 |

- 가장 크게 움직인 변경: 월 없는 기한과 요일 기한 계산(PR #343)
- 실패했던 문항을 고쳐 3/3으로 만든 예: 담당자 미정 업무(PR #346), 진행 중 업무 재언급(PR #327)

## 슬라이드 6. 한계: 숫자 뒤에 있는 것

- 추출 정밀도 80.3%는 목표를 0.3%p 넘은 경계값이고, 측정마다 80.3~86.4%였다
- 업무 하나를 여러 티켓으로 쪼개는 초과 25건이 남아 있다(30min_1 10건, 나머지 6개 문항 1~3건)
- 같은 평가셋으로 고치고 같은 평가셋으로 쟀고, 일부 프롬프트 예시가 평가 문항과 구조가 비슷하다. 처음 보는 회의록에서의 일반화는 확인하지 못했다
- 중복 판단은 18회 표본이라 14/18~18/18로 움직였고, 평가는 제품의 서버 경로를 모두 덮지 않는다(서버 경로에서 초안 제목 뒤바뀜 발견)
- 운영 지표(중복 발행률, 오발행률)는 측정하지 않았다
- 중복 판단 처리 시간은 라운드 2에서 14.4초로 목표(13.7초)를 0.7초 넘었다

# 예상 질문 5개

1. 담당자를 왜 AI가 추측하지 않고 멈추게 했나? 담당자 미정 업무는 참석자 중 한 명을 추측하면 잘못된 사람에게 티켓이 가고, 발행 뒤에는 되돌리기 어렵다. 그래서 "담당 지정 필요"로 멈추고 업로더가 정한다(평가 문항 ev19, 최종 측정 3/3).
2. 같은 평가셋으로 고치고 같은 평가셋으로 쟀는데 믿을 수 있나? 믿기 어렵다는 지적이 맞다. 그래서 한계 슬라이드에 적었고, 따로 떼어 둔 검증용 평가셋은 만들지 못했다. 다음 단계는 평가셋 밖 입력으로 한 번 더 확인하는 것이다.
3. 중복 판단은 표본이 너무 작지 않나? 6문항 x 3회 = 18회라 작다. 같은 코드가 14/18~18/18로 움직였고, 그래서 한 번의 수치로 달성을 단정하지 않고 범위로 적었다.
4. 서버 경로에서 초안 제목이 뒤바뀐다고 했는데 어떻게 대응하나? 추출 결과(담당자, 기한, 근거)는 91/91로 맞고 초안 제목과 본문이 가끔(10회 중 3회) 다른 업무의 것이 된다. 담당자가 확인 단계에서 카드를 보고 걸러낼 수 있고, 원문 업무와 대조해 어긋나면 다시 쓰게 하는 수정이 다음 단계다.
5. 회의록 안에 악의적인 지시문이 있으면? 원문을 데이터 태그로 감싸 지시를 무시하게 하고, 초안에 원문에 없는 URL이나 명령어가 생기면 경고한다. 평가 문항 ev29(이슈 20개를 만들라는 지시)는 최종 측정 3/3, 서버 경로 2/2에서 따르지 않았다. 완벽한 방어는 아니고, 발행은 담당자 확인을 거쳐서만 된다.
